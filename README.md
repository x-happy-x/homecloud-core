# Прототип локальной фототеки для Windows

Подготовлен 12.09.2026. Проверено оборудование: NVIDIA RTX 5080, 16 ГБ VRAM,
драйвер 591.86, доступен Python 3.10.6. Значение CUDA 13.1 в nvidia-smi —
возможность драйвера, а не подтверждение установки CUDA/cuDNN для Python.

## Фактический статус подготовки

Окружение, модели и тестовый фотосет уже установлены. Детектор и распознавание
проверены профилем ONNX Runtime: оба реально выполняют CUDA-операции на RTX 5080.
Полный тест обработал 545 фото LFW за 46,4 секунды, нашёл 650 лиц без ошибок.
Повторный проход пропустил все 545 неизменённых файлов и не создал дублей.

После перехода на HDBSCAN получено 26 предварительных групп, вне групп осталось
68 лиц вместо 109. Из 545 главных лиц только одно не сгруппировано; смешанных
эталонных групп нет, ARI — 0,9979. Ранняя оценка 0,6023 была некорректной: она
приписывала имя из папки также случайным лицам на заднем плане. Это всё равно
тестовая выборка, а не обещание точности на семейном архиве. Полные метрики —
в `test-results.json`, источники и контрольные суммы — в `assets-manifest.json`.

## Правила путей

`pathrules.py` держит чёрный и белый списки (настройки `block_paths` и
`allow_paths`, по строке на правило).

- Строка без масок — папка целиком (сам путь и всё внутри), со звёздочками —
  `fnmatch`-маска. Сравнение идёт по приведённому виду: нижний регистр и прямые
  слэши. Путь исключён, если попал в чёрный список и не попал в белый.
- Проверять правила прямо в SQL нельзя: `LOWER()` в SQLite не трогает кириллицу,
  а `GLOB` чувствителен к регистру. Поэтому отметка материализуется в колонке
  `photos.blocked`, а выборки просто добавляют `COALESCE(photos.blocked,0)=0`.
  `pathrules.apply(db, values)` пересчитывает отметки целиком: на 79 тысячах
  строк это около 0,6 с, поэтому вызывается прямо при сохранении настроек —
  галерея обновляется без пересканирования.
- Правила читают все, кто ходит по диску: обход в `prototype.py scan` (и прямой,
  и по описи), `catalog_index.walk`, кандидаты дубликатов, визуальный этап и
  этап 18+. Файлы при этом остаются на месте — правило только про библиотеку.

## Скрытый альбом и дубликаты

- Кто смотрит, бэкенд узнаёт из заголовков `X-HomeCloud-User` и
  `X-HomeCloud-Role`: их ставит фронт на Proxmox, который один и держит сессии
  картотеки. Заголовки браузера при этом всегда перезаписываются, подделать их
  через интерфейс нельзя. Сам бэкенд на 18311 по-прежнему рассчитан на домашнюю
  сеть: прямые запросы к нему в обход фронта ничем не проверяются.
- `privacy.py`: таблица `hidden_photos(path, owner, stored, hidden_at)`. Ключ
  каталога (исходный путь) не меняется — к нему привязаны лица, альбомы и
  анализ; переезжает только файл, его новое место лежит в `stored`. Всё, что
  отдаёт медиа, спрашивает `App.file_for(path)`. Скрытое не попадает ни в
  обычную галерею, ни в раздел «Люди» (`App.masked_faces`), ни в дубликаты;
  `?hidden=1` показывает свой альбом, администратору — все.
- `duplicates.py`: таблица `photo_hashes(path, size, modified, sha1, dhash,
  width, height)`. Точные копии ищутся по sha1, но считается он только для
  файлов, чей размер встречается больше одного раза — иначе пришлось бы
  прочитать весь диск. Похожие — по dHash 8×8; кандидатов подбирает разбиение
  хеша на четыре части (при расхождении до трёх бит одна часть обязана
  совпасть), поэтому сравнений не миллиарды.
- Считает `DuplicateService` в отдельном потоке: `POST /api/duplicates/scan`
  (`similar` — искать и похожие), `GET /api/duplicates/status` с прогрессом,
  `GET /api/duplicates` отдаёт группы страницами. В группе карточки готовятся
  только для первой дюжины копий, а размер «лишнего» считается по всем.
  На каталоге из 79 тысяч: 59 771 кандидат, около двух минут, 16 092 группы,
  выдача страницы — полсекунды.
- `POST /api/photos/hide` и `/api/photos/reveal` переносят файлы; удаление
  снимка чистит записи и в `hidden_photos`, и в `photo_hashes`, а корзину
  получает файл по фактическому адресу.

## Видео и настройки каталога

Ролики разбираются тем же этапом «Лица»: `video_tracks.py` идёт по всему
ролику и связывает находки в треки, `prototype.py scan` сохраняет их в
`faces` наравне с лицами на фото.

- Декодер — OpenCV (он уже стоит ради InsightFace), отдельный ffmpeg не нужен.
  Кириллица в пути OpenCV 4.11 не мешает, но на всякий случай есть запасной
  вариант через короткое имя Windows.
- **Лица ищутся не в горстке кадров, а по всей длине ролика** (по умолчанию
  дважды в секунду, `video_track_step`). Последовательные находки связывает
  `video_tracks.Tracker`: сначала по пересечению рамок с прошлым кадром, а
  если лицо на миг пропало из виду — по схожести эмбеддинга с уже
  накопленным треком (закрывается через `video_track_gap` секунд без
  продолжения). Для каждого трека берутся до `video_track_best` самых
  уверенных кадров, их эмбеддинги усредняются. На реальном ролике 11
  разрозненных карточек одного человека стали 4 связных трека.
  Перемотка на каждый нужный кадр (`CAP_PROP_POS_FRAMES`) на такой плотной
  выборке оказалась в разы медленнее последовательного чтения (3.2 кадра/с
  против 10–45) — детектор идёт по видео подряд, а лишние кадры между
  нужными не декодируются полностью (`grab()` без `retrieve()`).
- В каталоге: `photos.kind` (`photo`/`video`), `photos.duration`,
  `faces.frame_time` — секунда самого уверенного кадра трека, и
  `faces.track_start`/`faces.track_stop` — промежуток, в который лицо было
  в кадре (`NULL` у фото и у записей со старой покадровой схемой). Колонки
  досыпаются в существующую базу при первом запуске.
- Сопоставление при повторном скане: у фото и старых покадровых записей —
  рамка внутри одного кадра, как раньше. У треков рамка за время трека
  успевает уехать, поэтому сравнение другое — пересечение по времени
  (с запасом) плюс похожесть эмбеддинга (порог 0.55, тот же порядок, что и
  у кластеризации). Имя, присвоенное треку, переживает пересканирование.
- У роликов своя подпись кэша: изменили параметры трекинга — пересчитаются
  только видео, фотографии останутся нетронутыми. Смена схемы с покадровой
  на трековую сама по себе меняет подпись, так что первый скан после
  обновления пересчитает видео заново — старые покадровые лица без имён
  будут заменены треками.
- Замер на 20 реальных роликах (11 минут видео, в основном без лиц):
  4.1x реального времени. На весь архив (126ч) это около 30 часов счёта.
- Остальные этапы (визуальный индекс, OCR, описания, 18+) тоже умеют в видео:
  каждый вместо `Image.open(path)` берёт `video.open_frame(path)` из `video.py`
  — для фото это тот же самый файл, для видео представительный кадр (обложка).
  Дальше вся модель работает как обычно, без специального кода под видео.
  Проверка 18+ (`adult_photos.py`) — исключение: `video.sample_images(path, n)`
  берёт `adult_video_frames` кадров по всей длине, каждый прогоняется через
  NudeNet+WD-tagger по отдельности, и в каталог попадает кадр с самым высоким
  по строгости рейтингом (`RANK`) — иначе откровенный момент в середине ролика
  можно не заметить, посмотрев только на превью.
- `settings.py` хранит настройки в таблице `settings` того же каталога, поэтому
  их видят и бэкенд, и скрипты этапов: `video_enabled`, `video_track_step`,
  `video_track_gap`, `video_track_best`,
  `video_min_seconds`, `video_max_seconds`, `adult_video_frames`, `min_side`,
  `min_kilobytes`, `max_ratio`, `ignore_patterns`, `caption_backend`,
  `caption_model`, `caption_lmstudio_url`. `GET`/`POST /api/settings` читают и
  пишут их, значения приводятся к типу и зажимаются в разумные пределы.
- Описание (`caption_photos.py`) можно считать двумя способами:
  `caption_backend=local` — своя видеокарта, модель Hugging Face из локального
  кэша (`--model`, по умолчанию `Qwen/Qwen3-VL-2B-Instruct`, offline);
  `caption_backend=lmstudio` — HTTP-запрос на уже запущенный LM Studio
  (`caption_lmstudio_url`, обычно `http://127.0.0.1:1234/v1/chat/completions`)
  с именем загруженной там модели в `caption_model`. Второй вариант не трогает
  torch/transformers вовсе — кадр кодируется в data-URL и уходит в `messages`
  как `image_url`, как в `lmstudio_caption_eval.py`. Ошибка HTTP или недоступный
  сервер пишется в `photo_analysis.error`, не роняя весь проход.
- Отдача: `/media/photo?path=…&t=<секунда>` — кадр ролика картинкой (обложка и
  портреты лиц), `/media/video?path=…` — сам файл с поддержкой `Range`, иначе
  браузер не умеет перематывать. Блюр 18+ у обложки ролика работает так же, как
  у фото — `send_photo()` раньше сбрасывал `blur` для видео ещё до
  `render_preview()`, из-за чего небезопасная обложка никогда не замыливалась;
  теперь `blur` доходит до конца, и там читается тот же `rating`/`regions_json`.

## Альбомы и папки

`albums.py` держит ручные подборки и дерево папок каталога.

- Таблицы `albums(id, parent_id, title, created)` и `album_photos(album_id,
  path, added)`. `parent_id = 0` — верхний уровень, вложенность до восьми
  уровней, один снимок может лежать в любом числе альбомов.
- `GET /api/albums` отдаёт плоский список сверху вниз: `depth`, `trail`
  («2010 год / Отпуск»), `photos` (свои), `total` (с вложенными) и обложку —
  самый свежий добавленный снимок, при пустом альбоме берётся из вложенного.
- `POST /api/albums/{create|rename|move|delete|photos}` меняют дерево и состав;
  каждый ответ возвращает всё дерево заново, чтобы интерфейсу не пришлось
  запрашивать его отдельно. `move` не даёт вложить альбом в самого себя,
  `delete` убирает и вложенные, файлы при этом не трогаются.
- `GET /api/folders?path=` — дети одной папки и «хлебные крошки» до неё.
  Дерево собирается из `photos.dir` (около 4,6 тыс. папок) и кэшируется до
  следующего изменения каталога, поэтому ответ идёт за миллисекунды.
- Фильтры галереи: `folder=` (плюс `folder_deep=0`, чтобы взять только саму
  папку) и `album=` (плюс `album_deep=0`). Оба ложатся прямо в SQL, в том числе
  в ветку «фотографии человека», так что условия складываются без выборки всего
  каталога: человек + папка на 78 тыс. снимков считается за 55 мс.
- В карточке снимка появилось поле `albums` — список `{id, title, trail}`,
  чтобы просмотрщик показывал, где снимок лежит.

## Что здесь есть

- `prototype.py doctor`: диагностика runtime и доступных провайдеров.
- `scan`: рекурсивный обход JPEG/PNG/WebP, EXIF-поворот, детекция, embeddings,
  SQLite и миниатюры лиц. Оригиналы открываются только для чтения.
- Пропуск уже обработанных неизменённых файлов; повторный запуск после Ctrl+C.
- Контроль версии моделей через SHA-256. Неудачные файлы помечаются в SQLite.
- `gallery`: предварительные группы HDBSCAN, локальная HTML-галерея; совпадения
  внутри каждой группы отсортированы по уверенности. DBSCAN оставлен как опция.
- Нет облачных API и автоскачивания моделей. Телеметрия ONNX Runtime отключается.

Это экспериментальный код, не готовый менеджер фототеки. Вес моделей и первый
прогрев дают около 30 секунд накладных расходов при каждом запуске; затем идёт
обработка фотографий. Отдельные служебные операции ONNX Runtime могут выполняться
на CPU — это нормальное поведение, основные CUDA-операции подтверждены профилем.

## Подготовка среды

В PowerShell из этой папки:

```powershell
.\setup.ps1
```

Установка использует интернет только для зависимостей. Из-за ограничения Windows
на длину путей среда создаётся по короткому пути `work\v` в корне рабочего проекта.
Системный Python и драйверы скрипт не меняет.
Используется готовый официальный wheel InsightFace 1.0.1. Скрипт удаляет CPU-пакет
onnxruntime из собственной среды и переустанавливает GPU-пакет, поскольку эти
две дистрибуции используют одно имя Python-модуля.

Зависимости заданы диапазонами для начального эксперимента. После успешного
GPU-теста сохранить точные версии в lock-файл; пока это не проверенная связка.

## Модели

Локальные модели SCRFD и ArcFace из пакета buffalo_l уже находятся в
`models/buffalo_l/`. Сканер сам ничего не скачивает и не обращается к облаку.

Публичные pretrained-модели InsightFace имеют отдельные условия
`non-commercial research only`. Выбор конкретных весов и проверка их лицензии
необходимо учитывать. Веса загружаются отдельно для исследовательского эксперимента.

Явная подготовка онлайн: `python prepare_assets.py`. Этот скрипт скачивает официальный
пакет buffalo_l и архив LFW по ссылке из scikit-learn, проверяет SHA-256 LFW и
распаковывает тестовую выборку 20 людей, до 30 фотографий каждого. Сканер при этом
остаётся офлайн. LFW содержит публичные фотографии известных людей; права на
исходные снимки принадлежат правообладателям. Набор предназначен здесь только
для теста, не для распространения как собственной фотоколлекции.

- https://github.com/deepinsight/insightface/tree/master/python-package
- https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html

## Первый запуск

Для своей выборки (сначала лучше 500–1000 фотографий) выполните:

```powershell
.\scan-photos.ps1 -Photos "D:\PhotoSample" -Limit 1000
```

После завершения откройте `my-catalog\gallery.html`. Оригиналы не перемещаются
и не изменяются. Каталог и миниатюры хранятся отдельно в `my-catalog`.

По умолчанию группа создаётся минимум из трёх лиц. Если в большой фототеке
появляется слишком много мелких сомнительных групп, используйте более строго:

```powershell
.\scan-photos.ps1 -Photos "D:\PhotoSample" -MinClusterSize 5
```

Чтобы заново выполнить встроенную проверку на скачанном наборе:

```powershell
.\run-test.ps1
```

## Ручная разметка людей

Веб-интерфейс называется **HomeCloud**, живёт на хосте Proxmox (`s1`, 192.168.99.10)
рядом с bigfam в `/opt/homecloud`; служба `homecloud.service` слушает порт 4180.
Здесь, на Windows, остался только бэкенд: API, медиа, модели и каталоги.

Запуск бэкенда:

```powershell
.\backend.ps1
```

Он слушает `0.0.0.0:18311`, отдаёт только `/api` и `/media` и не открывает
браузер. Первый запуск создаёт `backend-token.txt` — общий секрет с прокси на
Proxmox; после его пересоздания нужно заново выполнить `deploy.ps1` из
`C:\Users\amagomedsharipov\Desktop\claude\homecloud`.

Интерфейс открывается по адресу `http://192.168.99.10:4180/` с любого устройства
домашней сети. Миниатюры и оригиналы прокси тянет с этого компьютера на лету,
поэтому при выключенной винде галерея покажет «Бэкенд HomeCloud недоступен».
Внешних CDN, аналитики и облачных API по-прежнему нет; изменяющие запросы
защищены токеном процесса и проверкой Origin.

Вход в интерфейс — по учётной записи картотеки BiGFaM: отдельных паролей у
HomeCloud нет, роль `viewer` видит каталог только на чтение. Имя человека можно
выбрать прямо из картотеки; тогда в `catalog.sqlite` у записи `people`
заполняется `bigfam_id` и карточка показывает портрет из картотеки. Обратно тоже:
в карточке картотеки появляется кнопка «Из HomeCloud» — аватарку можно взять
из найденных кадров, бэкенд отдаёт портретный кадр через `/media/face-crop/<id>`.

Исходники интерфейса и скрипт публикации:
`C:\Users\amagomedsharipov\Desktop\claude\homecloud` (см. README там же).

В Web UI доступны:

- запуск, остановка и возобновление очищенного сканирования `D:\trash`;
- живой этап работы, процент, текущий файл и счётчики лиц/ошибок;
- круглые аватарки людей (закреплённый кадр, портрет картотеки или первое лицо),
  лейбл «лиц/фотографий», имя «Фамилия И.О.» и годы жизни;
- выбор карточек и кадров долгим нажатием, обычный клик — открыть;
- светлая/тёмная тема;
- поиск людей, групп, имён файлов и папок;
- именование и объединение нескольких групп;
- перенос отдельных лиц к человеку и ручное исключение ошибок;
- отмена последнего действия;
- раздел проверки несгруппированных и исключённых лиц;
- просмотр фотографий и фильтр «кто на фото» по нескольким людям одновременно;
- открытие оригинала без изменения файла.

Классический Windows-интерфейс PySide6 остаётся запасным вариантом:

```powershell
.\people.ps1
```

По умолчанию он открывает `trash-catalog`. Для другого каталога:

```powershell
.\people.ps1 -Catalog ".\my-catalog"
```

В обоих интерфейсах можно назначить имя одной или нескольким выбранным группам,
объединить группы одинаковым именем, переназначить отдельные лица, исключить
ошибочные лица и отменить последнее действие. Двойной щелчок по миниатюре
открывает оригинальную фотографию. Имена и исправления сохраняются в SQLite,
но оригиналы остаются только для чтения.

Повтор `scan` продолжает обработку: лимит относится к числу новых попыток в запуске.
Держать `data` вне исходной фотопапки, желательно на SSD. После смены набора моделей
завершить переиндексацию перед группировкой.

## Опись и дерево файлов

`catalog_index.py` держит опись каталога: обход папок, сверку с прошлым разом,
дерево и исключения.

- `photos` получил колонки `dir`, `state` (`new`/`changed`/`known`/`missing`/
  `excluded`) и `last_run`;
- `photo_dirs` — счётчики по папкам (свои файлы, всё поддерево, новые,
  изменённые, пропавшие, исключённые, байты), чтобы дерево открывалось мгновенно;
- `scan_roots` — что сканировали и когда;
- `scan_exclusions` — исключённые папки и файлы.

Опись запускается как задание с `features={"inventory": true}`
(`device_job.py` умеет выполнить только её и выйти). API: `GET /api/device/tree`
(корни без параметра, содержимое папки с `?path=`), `POST /api/device/exclusions`
с `{"add": [...], "remove": [...]}`.

`take_inventory()` пишет найденное в `photos` порциями по ходу обхода (не одной
транзакцией в конце), поэтому остановка или сбой на середине не теряют уже
найденное — при желании прогон можно просто повторить, он доучтёт остаток.
Обход (`walk()`) не спускается в заблокированные `pathrules` папки вовсе (а не
просто отбрасывает их файлы постфактум) и обходит защиту от зацикливания на
junction/симлинках (частый случай на Windows — библиотеки Steam, папки
облачных синхронизаций), отслеживая уже посещённые папки по `(st_dev, st_ino)`.

Когда полностью сканируют более широкую папку (например, весь `D:\` после
того как раньше сканировали только `D:\trash`), прежние отдельные корни внутри
неё убираются из `scan_roots` — «Что найдено» не копит дубликаты вроде
`D:\xxx` рядом с `D:\`. Сами файлы и счётчики при этом не трогаются: вложенная
папка по-прежнему открывается через дерево родителя. Уборка происходит только
при полном (не остановленном) проходе — частичный обход широкого корня не
имеет права списывать более точные данные уже завершённых узких корней.

Файл, который на этом проходе не обходили (правило путей в настройках,
служебная папка вроде `$RECYCLE.BIN`/`System Volume Information` из
`EXCLUDED_NAMES` или `scan_exclusions`), не считается пропавшим — иначе
любое исключение пути превращало бы тысячи вполне живых файлов в «missing».
`take_inventory()` перед тем, как пометить файл пропавшим, проверяет все три
источника исключений и ставит `status='excluded'`, если хоть один сработал;
`status='missing'` остаётся только для файлов, которых по-настоящему больше
нет на диске. Реклассификация обновляет `last_run`, чтобы те же строки не
пересчитывались заново на каждом следующем скане.

Исключение — свойство каталога: файлы получают `status='excluded'`, поэтому
визуальный индекс, OCR, описания и 18+ их не видят (они выбирают `status='ok'`),
а `prototype.py scan` дополнительно обходит исключённые папки стороной и
пропускает исключённые файлы.

## Речь в видео

`speech_videos.py` расшифровывает сказанное в ролике: получаются субтитры и
поиск по словам наравне с текстом на снимке. Запускается как обычный этап
задания (`--features` с `speech`) из своего окружения `work/audio-venv`.

Звук берётся прямо из видеофайла через PyAV, который приезжает вместе с
faster-whisper, — отдельный ffmpeg ставить не нужно. Распознаёт Whisper
large-v3 на видеокарте: на RTX 5080 выходит около тридцати минут записи за
минуту счёта.

Две особенности Whisper пришлось обойти прямо в этапе:

- **Он договаривает за тишину.** На беззвучном ролике модель выдаёт
  «Thank you.» или «Продолжение следует...» длиной в доли секунды. Реплика
  принимается, только если сама модель считает её речью: короткие,
  неуверенные и помеченные как «не речь» отбрасываются.
- **Он путается в языке.** Определение по первым тридцати секундам ветра и
  хлопков дверей уверенно называет норвежский, и распознавание уезжает
  вместе с ним. Язык определяется по уже найденной речи, а когда
  уверенности мало — берётся язык архива (`speech_fallback_language`).

Результат лежит в двух таблицах: `video_speech` — весь текст ролика одной
строкой (по нему ищут) и состояние обработки, `video_speech_segments` —
реплики с таймкодами и разбивкой по словам. Реплики отдаёт `/api/speech`
отдельным запросом: в списке галереи они не нужны, а в ролике их бывает
много.

У ролика без речи язык не записывается вовсе — иначе потом придётся
объяснять, почему домашнее видео помечено как норвежское.

## Разделение голосов

`speaker_diarization.py` раскладывает дорожку ролика на говорящих —
SPEAKER_00, SPEAKER_01 и так далее — и считает голосовой эмбеддинг на
каждого. Запускается вторым этапом после речи (`--features` с `diarize`),
из того же окружения `work/audio-venv`.

Модель — `pyannote/speaker-diarization-community-1`, закрытая: нужен токен
HuggingFace и принятое на странице модели соглашение. Токен лежит в
`hf-token.txt` рядом со скриптом (в `.gitignore`, в git не попадает) —
альтернативно берётся из `--hf-token` или переменной `HF_TOKEN`.

Метки говорящих существуют только внутри одного ролика: `SPEAKER_00` в двух
разных файлах — не обязательно один и тот же человек. Постоянная личность
появится на этапе связки голоса с лицом, когда эмбеддинг будет с чем
сравнивать (`voice_prints`); здесь эмбеддинг только сохраняется, готовый к
такому сравнению.

Раз диаризация и распознавание речи разбирают одну и ту же дорожку, репликам
из `video_speech_segments` сразу проставляется метка говорящего — по тому,
чей интервал перекрывает реплику дольше всего. Отдаёт это `/api/speech`
вместе с текстом.

На длинных роликах со сменой акустики pyannote иногда разводит одного
человека на два кластера. После диаризации близкие по эмбеддингу кластеры
внутри одного ролика склеиваются автоматически (`merge_close_speakers`,
порог косинуса 0.6) — на реальном случае похожесть внутри такой пары была
0.69–0.70, между разными людьми 0.12–0.31, разница с запасом.

## Связка голоса с лицом

Продолжение диаризации: `speaker_diarization.link_speakers_to_faces()`
смотрит, чьё лицо было единственным в кадре, пока говорящий говорил.
Совпало для большинства его реплик — связь сохраняется в
`video_speaker_faces` (path, speaker, face_id, confidence). Два лица в
кадре или ни одного в конкретной реплике — она просто не голосует, решение
не гадается.

Человек за ролик обычно не раз выходит из кадра и возвращается — у каждого
появления свой `face.id` (трек, этап 3), но голос один. Голосование по
отдельным face_id размывало бы перевес между ними до нуля, поэтому
`face_groups()` сперва группирует треки по уже подтверждённому человеку
(`face_people`): если все появления названы одним именем — они и голосуют
вместе. Непоименованные треки остаются каждый сам за себя: неизвестно,
один ли это человек в разных появлениях или разные.

Как только голос связан с названным лицом, его эмбеддинг пополняет
`voice_prints(person_id, embedding, dims, samples, updated_at)` —
постоянный образец человека, не ролика: скользящее среднее, взвешенное по
числу подтверждённых случаев. С этого момента `suggest_from_voice()`
сравнивает голос каждого нового говорящего с образцами и, если похоже
(порог 0.55), предлагает имя даже там, где лица не видно вовсе —
`video_speakers.suggested_person_id`/`suggested_confidence`. Это подсказка,
не факт: `/api/speech` отдаёт её отдельно от связки через лицо
(`source: 'voice'` против `source: 'face'`), и интерфейс показывает её
иначе — со знаком «?» и уверенностью по наведению.

## Ручное назначение голоса

Автоматическая связка (`link_speakers_to_faces`) срабатывает не всегда — ей
нужно ровно одно лицо в кадре на большинстве реплик говорящего. Когда этого
не случилось, назвать голос можно руками: `POST /api/photos/assign-speaker`
(`path`, `speaker`, `name`, `bigfam_id`) находит или создаёт человека той же
логикой, что и назначение лиц (`CatalogStore.find_or_create_person` — общий
код для обоих путей), помечает `video_speakers.assigned_person_id` и сразу
пополняет `voice_prints` этим образцом: ручное подтверждение так же ценно,
как и связка через лицо.

`/api/speech` разбирает источники по порядку доверия: назначено руками →
связано через лицо → похоже по голосу (только предположение, ничем не
подтверждено). Каждый следующий уровень заполняет то, что не решил
предыдущий.

## Поиск снимка в интернете

`reverse_search.py` + `POST /api/photos/search-upload` — временная публичная
ссылка на снимок для «искать в Яндексе/Google/Bing по картинке». HomeCloud
принципиально не выходит в интернет сам по себе, поэтому у файла нет адреса,
который можно отдать поисковику; здесь бэкенд на время заливает JPEG-копию
(для видео — тот же представительный кадр, что и у остальных этапов) на
Litterbox (временный раздел catbox.moe, без регистрации, случайная
неугадываемая ссылка) и отдаёт фронтенду прямую ссылку на файл.

Проверены на месте и отброшены: **0x0.st** недоступен с этой сети (похоже, в
блок-листах как типичный анонимный дамп-хостинг), у **file.io** публичный
анонимный приём файлов сейчас не отвечает как раньше, **tmpfiles.org**
принимает файл, но отдаёт HTML-страницу вместо самой картинки — для поиска по
URL нужна именно прямая ссылка на байты изображения, а не обёртка. Litterbox —
единственный из проверенных, что и принял файл, и вернул рабочую прямую
ссылку с верным `Content-Type: image/jpeg`.

У анонимных заливок в Litterbox нет ручного удаления — только истечение
срока, и самый короткий поддерживаемый сервисом срок — час (не «пара минут»,
как изначально хотелось); это и используется.

На этой машине обычная проверка TLS-сертификата виснет на рукопожатии при
обращении к внешним сайтам (похоже на антивирус с проверкой HTTPS или похожее
ПО, подменяющее сертификат) — с явного согласия пользователя проверка
отключена (`ssl.CERT_NONE`), но только для этого одного модуля; больше нигде
в приложении сертификаты так не ослабляются.

## Как ставится рейтинг 18+

Мнения две штуки и они независимы: NudeNet ищет области тела, WD-tagger смотрит
на картинку целиком. Поодиночке оба врут — детектор находит «грудь» на тексте и
мебели, теггер выдаёт высокий `explicit` на сканах и скриншотах. Поэтому:

- одиночной области верим только с запасом (≥ 0.62) и только если теггер не
  спокоен (`safe ≥ 0.9` при низких questionable/explicit, либо тег `no humans`);
- слабой области (≥ 0.45) — если теггер сам склоняется к небезопасному;
- одному теггеру — только когда небезопасная оценка у него лидирует;
- крошечные рамки (меньше 0.6 % площади кадра) отбрасываются;
- если областей тела нет вовсе, а теги говорят про текст и интерфейс
  (`english text`, `fake screenshot`, `wall of text`, `no humans` и подобные) и
  нет ни одного телесного тега — снимок безопасен, что бы теггер ни выдал;
- `sensitive` («на грани») в подборку 18+ и под блюр не попадает, это только
  пометка в сведениях.

Блюр рисуется на лету в `/media/photo?blur=...` по сохранённым рамкам
(`[x, y, ширина, высота]`). Пороги там ниже, чем у рейтинга: интимные области
закрываются с 0.25, обнажённые — с 0.35, рамка расширяется на 22 %, а кусок
сначала пикселизуется и только потом размывается. Если кадр считается
небезопасным, но закрывать нечего (детектор ничего не локализовал), размывается
весь кадр — оставлять «как есть» нельзя. Режим «блюр и непроверенных» в галерее
закрывает целиком всё, что этап 18+ ещё не смотрел.

Пересчитать рейтинги по уже сохранённым тегам и областям, не запуская модели:

```powershell
..\..\workision-venv\Scripts\python.exe adult_photos.py --catalog trash-clean-catalog --recheck
..\..\workision-venv\Scripts\python.exe adult_photos.py --catalog trash-clean-catalog --recheck --apply
```

## Превью вместо оригиналов

`/media/photo` умеет отдавать уменьшенную копию: `&size=<пиксели>` округляется
до ближайшей ступени (240, 400, 640, 960, 1440, 2200) и кэшируется на диск в
`<каталог>/previews/<xx>/<ключ>.jpg`. Ключ — это путь, время файла, размер и
режим блюра, поэтому при изменении снимка копия обновляется сама, а в ссылке
есть `&v=<время>`, и браузеру разрешено держать её неделю.

JPEG разбирается через `draft()` — сразу в уменьшенном виде, без раскодирования
полного кадра. Копии удаляются вместе со снимком.

Галерея просит размер под плитку (ступень зума × плотность экрана), просмотрщик —
под размер окна, лента — 120 px. Оригинал уходит только по кнопке «Оригинал».

## Откуда пауза перед поиском лиц

Модели грузятся быстро: две сессии ONNX Runtime на CUDA поднимаются примерно за
секунду (хеш моделей — 0.1 с, сессии — 0.3 с, прогрев — 0.4 с). Длинная пауза в
начале — это обход диска: `prototype.py scan` собирал список файлов целиком,
ничего не публикуя, а интерфейс в это время писал «Подготовка модели», потому что
общее число файлов ещё не известно.

Теперь обход отчитывается о ходе (каждые 20 папок: сколько файлов найдено и где
идёт), а при готовой описи его можно не делать вовсе — ключ `--use-inventory`
берёт список из каталога. `device_job.py` подставляет этот ключ сам, если папка
есть в `scan_roots`, так что после шага «Собрать список файлов» поиск лиц
начинается сразу.

## Повторные запуски

Каждый этап помнит версию файла, для которой он уже отработал, и при следующем
запуске её пропускает:

| Этап | Где хранится отметка | Что считается изменением |
| --- | --- | --- |
| лица | `photos.size/modified/model` | размер, mtime или модель детектора |
| визуальный индекс | `photo_analysis.size/modified/embedding_model` | то же плюс смена SigLIP |
| OCR | `photo_analysis.ocr_status` | сброс при переиндексации изменённого файла |
| описания | `photo_analysis.caption_status` | подробный JSON Qwen с уверенными WD-тегами |
| 18+ | `photo_adult_analysis.size/modified` | размер или mtime |

NudeNet внутри читает файл через `cv2.imread`, а тот на Windows возвращает
`None` для путей с кириллицей — получалось `'NoneType' object has no attribute
'shape'` на каждом снимке из русских папок. Теперь детектору отдаётся уже
открытый через PIL кадр (BGR), и заодно с учётом EXIF-поворота.

Изменился файл — визуальный индекс пересчитывает строку и заодно обнуляет
`ocr_status`, `caption_status`, текст и описание, поэтому они пересчитываются
следующими этапами. Этап, упавший на снимке, повторяется при следующем запуске.

Источники заданий пишутся в таблицу `scan_runs` того же каталога: корни, список
выбранных снимков, когда запускали, какие этапы дошли до конца. Их отдаёт
`GET /api/device/history`, забывает `POST /api/device/history/forget`, а
интерфейс показывает списком в диалоге сканирования. Если сервер перезапустили
посреди задания, запись подхватывается обратно по файлу прогресса.

У каждого скрипта (`prototype.py scan`, `analyze_photos.py analyze`,
`ocr_photos.py`, `caption_photos.py`, `adult_photos.py`) есть `--force`,
который снимает эту защиту; `device_job.py --force` передаёт флаг всем этапам,
а в интерфейсе он включается галочкой «Переделать заново».

## Группы и имена при повторном скане

Лицо — это строка `faces` с постоянным `id`, к которому привязаны имя
(`face_people`), исключение и аватарка. Поэтому повторный проход по фотографии
не удаляет её лица, а **сопоставляет** новые рамки со старыми по IoU (порог
0.45): совпавшие строки обновляются на месте, новые добавляются, пропавшие
удаляются. Раньше здесь были `DELETE` + `INSERT`, и любой повторный скан
обрывал `face_people` каскадом — имена исчезали.

Подпись кэша (`photos.model`) теперь зависит только от модели и `--min-side`:
списки исключений решают, какие файлы обходить, и на результат для конкретного
файла не влияют. Старые подписи `scan-filters-v1` переносятся на новую при
первом же запуске, без пересчёта.

Метки кластеров лежат в таблице `face_clusters` (`label`, `probability`,
`method`). При старте ничего не кластеризуется: читаются готовые метки, а
HDBSCAN считается только для лиц без метки — порциями по 4000, причём каждая
порция сначала притягивается к центроидам существующих групп (косинус ≥ 0.66),
и только остаток кластеризуется заново. Поэтому ключи `auto:<label>` стали
стабильными между запусками, а старт перестал зависеть от размера каталога
(6237 лиц: 12 с раньше, 0.1 с сейчас).

Полная пересборка — отдельная команда: `POST /api/recluster` или кнопка
«Пересобрать группы» в разделе «Люди». Она удаляет метки и считает HDBSCAN по
всему каталогу (6237 лиц — около 12 с). Имена и исключения при этом не
страдают: они привязаны к лицам, а не к группам.

Потолок на всякий случай остался: `--max-faces` у `web_server.py` и `-MaxFaces`
у `backend.ps1`; по умолчанию `0` — без ограничения.

## Сравнение людей

Три запроса поверх тех же векторов:

- `GET /api/similar?key=<группа>&limit=10` — ближайшие группы по центроиду;
- `GET /api/similar-pairs?limit=20&min=0.38&named=0` — самые похожие пары
  каталога, кандидаты на объединение;
- `GET /api/compare?a=<группа>&b=<группа>` — центроидная близость, лучшая и
  типичная пара кадров, шесть самых похожих пар лиц и место пары среди всех пар
  именованных людей (`rank`).

Центроиды кэшируются по составу групп, поэтому запрос укладывается в десятые
доли секунды. Пороги словесных оценок: 0.62 — «скорее всего один человек»,
0.50 — «очень похожи», 0.38 — «заметное сходство».

## Если имена всё-таки потерялись

`restore_names.py` возвращает их по векторам: уцелевшие лица человека работают
образцами, к ним притягиваются похожие безымянные лица.

```powershell
..\..\work\Scripts\python.exe restore_names.py --data trash-clean-catalog          # показать
..\..\work\Scripts\python.exe restore_names.py --data trash-clean-catalog --apply  # записать
```

Порог `--threshold` (0.62) и запас `--margin` (0.05) правятся ключами. Каждый
человек пишется отдельным действием, поэтому «Отменить последнее действие»
в интерфейсе откатывает по одному.

## Мультяшные и игровые персонажи в группах

Детектор лиц иногда находит «лицо» на нарисованном персонаже, 3D-модели
или игровом скриншоте — в архиве со скачанным не-семейным контентом таких
попадается много, и они забивают «Люди» мусорными автогруппами.

`authenticity_photos.py` — отдельный этап (`--features` с `authenticity`,
своё окружение `work/imgutils-venv`), считает для каждого неназванного
лица `deepghs/anime_real_cls` (пакет `dghs-imgutils`, ONNX,
MobileNetV3-lite) на широком кропе вокруг лица — на тесной обрезке модель
путается и почти всё называет «реальным». Результат в `face_authenticity
(face_id, real_score, anime_score)`; `CatalogStore.groups()` (people_gui.py)
не показывает в автогруппах лица с `anime_score>=0.85` — тем же способом,
каким уже фильтруются `face_exclusions`. Кластеризация (HDBSCAN) при этом
не трогается, уже названные лица фильтр не касается вовсе.

Проверено на реальных данных каталога (не на глаз): 0.98 «real» на
настоящем человеке, 0.95–0.99 «anime» на мультяшных персонажах, визуальным
коллажем подтверждена чистота обеих сторон уверенности. Первой попытке
(SigLIP zero-shot на обрезке лица) в этом же README не место — честно не
сработала (33% согласия с файловой классификацией на случайной выборке,
хуже случайного гадания), поэтому взята готовая специализированная модель
вместо самодельного промпта.

Граница: модель отличает рисунок от фото, а не «есть ли здесь вообще
лицо» — маски, пейзажи, размытие она не ловит, это отдельный, всё ещё
открытый класс ложных срабатываний детектора.

## Ограничения прототипа

- Максимум 5000 лиц для группировки; для большой библиотеки нужен HNSW и
  пакетная организация кластеризации.
- HDBSCAN сам отделяет выбросы, но может оставить редкого человека без группы.
  `MinClusterSize=3` (было по умолчанию) на реальном каталоге дробил одного
  человека на осколки и плодил мусорные группы из ложных детекций: 1074
  автогруппы, из них 696 размером ≤5. На `MinClusterSize=8` — 313 групп,
  топ-группы выросли до 60–94 лиц, групп ≤5 почти не осталось (проверено
  полным recluster() на копии каталога при 3/5/8, сравнил размеры и на глаз
  через коллаж из случайных лиц группы). Новый дефолт — `8`.
- Параметр `Distance` используется только в резервном режиме DBSCAN; это
  расстояние, не вероятность совпадения. Все группы пока неподтверждённые.
- Есть первый GUI для имён и ручной коррекции, но пока нет поиска фотографий
  по нескольким людям, удаления исчезнувших файлов, отслеживания папок,
  HEIC/RAW/видео и фильтров EXIF.
- Один процесс сканирования на один каталог. SQLite commit выполняется на фотографию.
- Кэш старых или прерванных попыток пока автоматически не чистится.
- После перемещения оригиналов их пути считаются новыми.

## Критерии завершения эксперимента

1. Обе модели проходят GPU-прогрев и обработку реальных снимков.
2. Есть измерения времени и VRAM на выборке, а не предположения по GPU.
3. Повторное сканирование не увеличивает число лиц без изменений файлов.
4. Прерывание и продолжение сохраняют уже завершённые фотографии.
5. Снимки с EXIF-поворотом и кириллическими путями обрабатываются корректно.
6. При отключённой сети обработка и галерея работают.
7. Просмотрены ошибочные объединения и пропущенные совпадения; выбран порог.
